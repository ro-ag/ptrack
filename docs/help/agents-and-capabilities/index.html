    Explicit boundaries

    Coordinate agents without implying authority

    p-track connects agent activity to durable project context and offers narrowly typed host operations. Associations, ownership labels, worktree claims, handoffs, and workflow proposals remain coordination metadata; only a separately approved capability can authorize a matching broker call.

    Capabilities are not a shell sandbox. Ordinary terminal processes keep their normal operating-system access and may invoke tools such as curl, git, or ssh directly. p-track capability policy applies only when an agent calls a typed p-track broker tool.

    Launch agents and read run state

    On Board, use Launch agent in the plan header or the Agent action on a task. Choose an installed agent profile; p-track starts it in a new terminal tab linked to that plan or task. The task drawer shows linked terminal-backed agents alongside external agents registered with the current project.

    Overview presents bounded run information, including whether a run is terminal-backed or external, its lifecycle, process or lease state, current association, structured activity, and notifications. A run may remain in history after it exits or becomes stale, so a historical row is not evidence that an agent is still live.

    Treat associations as context, not permission

    An association points a live terminal session or agent run at project, plan, or task context. The persisted pointer contains IDs only: it has no token, environment, runtime output, project generation, or capability.

    Before accepting an association or using it for a linked mutation, the host resolves it against the current canonical project, workspace generation, live identity, and project catalog. A task must still belong to the named plan. Stale or mismatched associations are rejected instead of being reused.

    An association grants no authority. It describes where activity belongs. It does not authorize task changes, filesystem access, network access, commands, Git operations, or capability use.

    Use ownership and worktrees as advisory signals

    A live task-associated agent can claim or release task ownership in Overview. Ownership helps expose multiple agents working on the same task, but it is advisory. Claiming or releasing it does not change the agent, association, task status, process, or capabilities. An incomplete bounded snapshot cannot prove exclusive ownership.

    A live run can be associated with an existing worktree observed by the host. p-track verifies the current run and association revision, inspects the worktree, and confirms that the agent working directory is inside it. The claim is ephemeral presentation metadata, separate from both the run association and every capability decision.

    Associating a worktree does not create a worktree, move the agent, change its working directory, run a mutating Git command, or grant filesystem, network, or capability authority.

    Review handoffs and workflow proposals

    Overview can prepare a bounded handoff from one live agent to another. The inbox stores an immutable proposal and its preview. Sending it grants no authority and changes no task. Acknowledgment revalidates the exact proposal and removes that inbox item; it does not mutate project memory, task state, an agent, or a capability.

    Agents can also prepare validation, commit, pull-request, or merge workflow proposals. Preparing, approving, or dismissing one manages the proposal only. Approval executes no command or Git/hosting action, changes no task, and grants no capability. Perform the proposed work through the repository's normal, separately authorized workflow.

    Interpret drift and notifications

    Drift findings compare bounded, provider-neutral structured events with observable project and Git state. They are advisory signals, not proof that work is inside or outside scope. Overview marks incomplete snapshots; absence of a warning must not be treated as proof that no overlap or drift exists.

    Notifications identify normalized lifecycle conditions such as a question, approval request, failure, or completion. They help route attention but do not answer a question, approve an action, or alter an agent run.

    Understand agent event privacy and retention

    Structured event collection is enabled by default. Free-text event summaries are disabled by default. p-track retains at most the most recent 128 accepted events for a run and removes events older than 14 days under the default policy.

    The provider input is a closed structured contract. It does not accept raw provider JSON, prompts, messages, tool payloads, command arguments or output, transcripts, environment data, credentials, or hidden reasoning. Accepted fields are normalized and bounded; project paths must remain project-relative. Credential-like or reasoning-like content is rejected, and rejection messages do not echo the rejected input.

    Start from deny by default

    A capability belongs to one project and one agent profile. Every broker operation rechecks the stored grant, exact normalized scope, profile, enabled state, and approval expiry immediately before use. A missing, disabled, stale, mismatched, expired, or out-of-scope grant is denied.

    Capabilities authorize one typed family:

    • HTTP — exact origin, allowed methods, segment-bounded path prefixes, request and response limits, redirects, timeout, and concurrency.
    • Git — allowed operations plus the repository's freshly read remote name and URL, branches, and exact refspecs. Tag writes, ref deletion, and force behavior require separate explicit scope.
    • SSH — exact host, port, user, pinned host key, and individually approved operations such as Git-over-SSH, exact remote commands, upload, download, or forwarding targets. Local transfer paths must remain within separately approved project roots. Interactive shell transport is unavailable.

    One grant does not imply another. For example, an SSH upload approval does not approve download or a remote command, and a Git approval does not inherit an SSH grant unless the operation explicitly names and passes that separate grant.

    Preview, approve, expire, or remove a grant

    1. Create or edit the draft in Capabilities.
    2. Use Preview scope to inspect the normalized effective scope. Test connection is a separate explicit diagnostic.
    3. Use Save draft. A new draft is disabled and saving does not enable it.
    4. Enable only the exact previewed scope. Approval is bound to its digest and a bounded expiry window.
    5. Disable to revoke approval immediately, or let the approval expire. Authorization checks observe revocation and expiry on subsequent calls.

    A material edit to the security envelope disables the grant and clears its approval, requiring a fresh preview and enable action. Removing a capability deletes the grant but deliberately retains its bounded audit history.

    Call the typed broker

    The broker exposes ptrack_http_request, ptrack_git, and ptrack_ssh. From a p-track-launched agent terminal that has the broker session token, call one tool with a JSON object:

    ptrack capability call <tool> --arguments '{"capability_id": 1}'

    The arguments must match that tool's input schema and identify an enabled capability. The command fails outside a p-track agent terminal when the broker token or matching project descriptor is unavailable. Agent integrations that speak MCP can use the same tools over standard input and output:

    ptrack capability mcp

    Read audit metadata

    When auditing is enabled for a grant, p-track keeps a bounded record of sanitized operation metadata: capability and profile identity, kind, operation, sanitized target, success or error class, duration, byte counts, redirects, and time.

    The audit recorder has no fields for headers, bodies, terminal output, credentials, raw standard error, or raw arguments. HTTP targets retain only their origin; other targets are reduced to their sanitized typed identity.

    Boundaries at a glance

    FeatureWhat it recordsWhat it does not grant or execute
    AssociationValidated project, plan, or task context.No task, filesystem, network, command, or capability authority.
    OwnershipAn advisory task claim for a live run.No exclusive lock and no product mutation.
    Worktree claimA host-observed worktree containing the run's CWD.No worktree creation, CWD change, Git command, or authority.
    HandoffA bounded immutable proposal and preview.No task, memory, agent, or capability mutation.
    Workflow proposalA revalidated suggested workflow.No command, Git/hosting action, task change, or grant.
    CapabilityAn exact, time-bounded broker scope.No restriction on ordinary shell processes.
