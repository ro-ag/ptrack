    Installation, trust, and recovery

    Install and maintain p-track safely

    Install an official package for your platform, opt in before p-track contacts GitHub automatically, and keep project backups before opening older data with a newer schema.

    Install an official package

    Download the native package for your operating system and CPU from the official GitHub Releases page. Release archives contain the CLI, terminal dashboard, and Desktop GUI. Put the executable on your PATH.

    On macOS, you can instead open p-track_<version>_darwin_<arch>.dmg and drag p-track.app into /Applications. The executable inside the app bundle also provides the CLI.

    Use an official package. Source builds require Rust, Node, the Tauri prerequisites, and the repository's complete validation workflow. No Go runtime or toolchain is required.

    On macOS, Install 'ptrack' Shell Command… writes one managed block to ~/.zprofile. It appends the running app's binary directory to the end of the existing PATH, leaves an existing managed block alone, and takes effect in a new terminal session.

    Choose when to check, download, and install

    Manual update checks occur only when you select Check for updates. Automatic checks are off by default and persist only after explicit opt-in. They contact the stable releases for the fixed ro-ag/ptrack GitHub repository.

    The About & Updates dialog carries both surfaces: it identifies p-track, its version, its build, and its Apache-2.0 license, links to the project, license, Help Center, and issue tracker, and holds the check, download, and install actions. Open it from the version chip, Help ▸ Check for Updates…, or the native About item. The automatic-check opt-in is the same setting in that dialog and in Settings ▸ Updates.

    Consent is separated into three steps:

    1. A check discovers one newer stable release and the exact package for the running OS and CPU.
    2. A separate action downloads that exact candidate.
    3. A separate action hands off or applies that same verified version.

    A check never silently downloads or installs. Prereleases, drafts, development builds, downgrades, generated source archives, unexpected assets, and ambiguous candidates are rejected.

    Understand update verification

    Downloads are size-bounded and staged in a private directory under the global p-track home. p-track requires the expected archive layout, executable, platform machine type, and one exact SHA-256 entry from checksums.txt. It rejects links, extra or duplicate entries, path traversal, and digest mismatches, then reopens and rehashes staged files before use.

    The release checksum is not an independent publisher signature. The package and checksum are co-hosted in the same GitHub Release. On Windows and Linux, trust rests on the GitHub release account plus that checksum. On macOS, p-track additionally requires the pinned Developer ID identity and Gatekeeper acceptance for the whole DMG.

    • macOS: verifies and opens the complete DMG for installation; it never replaces one executable inside the signed app bundle.
    • Windows: revalidates the ZIP and reveals it in Explorer; close p-track and replace the executable manually.
    • Linux: updates only a safely owned standalone executable, using a target lock, verified rollback link, durable recovery journal, atomic replacement, version probe, and rollback on failure. It never uses sudo.

    Preserve update recovery state

    Interrupted stages are revalidated at startup. An unresolved journal, unsafe target, ambiguous backup, or excessive stage backlog enters recovery-required state and blocks new update work.

    When recovery is required, close p-track and inspect $PTRACK_HOME/updates or ~/.ptrack/updates together with the installation. On Linux, preserve each .pending-apply-*.json journal and sibling .ptrack-backup-* executable until the installed target is identified. Deleting either first may remove evidence needed for safe rollback. Reinstalling the same or a newer official package is the conservative fallback; do not copy a staged payload into place or bypass its verification.

    Local-first security boundary

    p-track has no cloud service account and does not send project planning data to a p-track-hosted service. Project records remain in local files. Desktop may expose private loopback endpoints for local agent-run integration while a project is active; their descriptors and session material are stored in the private per-project runtime directory.

    The updater does not accept project-supplied update URLs, store credentials, build from source, elevate privileges, or run unattended installation helpers. Update checks contact GitHub only through the manual or opted-in automatic flow.

    Privacy and bounded diagnostics

    Structured agent event collection is enabled by default; free-text summaries are disabled. The default policy retains the newest 128 accepted events and expires events older than 14 days. The closed event contract rejects raw prompts, messages, transcripts, tool payloads, command arguments or output, environment data, credentials, and hidden reasoning.

    Terminal workspace persistence stores layout and descriptors, not terminal screen contents.

    Set PTRACK_HOME to move the global store and its backups, runtime state, and update staging. WebView localStorage remains a separate application-browser store; it is not part of global.redb.

    All three records use a versioned envelope and are repaired field by field when partly invalid. A record p-track cannot read, or one written by a newer version, is reported and read as defaults rather than overwritten, so downgrading never destroys it. Settings ▸ Data & Diagnostics ▸ Reset Application State clears these records and the saved terminal workspaces. It does not touch plans, tasks, notes, backups, or the known-projects list. See the reset actions.

    Back up with the documented limits

    ptrack backup

    The command byte-copies the live project database to <global-home>/backups/<project>-<timestamp>.db and records the path in the global store. There is no built-in restore command.

    Do not overstate this backup. The implementation does not promise encryption, an atomic destination, or a transaction-consistent snapshot of concurrent writers. The copy excludes runtime state and WebView localStorage. Before a consequential manual restore, stop project writers, preserve the current database separately, and verify the chosen copy before replacing anything.

    Retired legacy databases

    Runtime commands resolve only the stores named by the attested active-generation marker. Retired bbolt-era files such as global.db or .ptrack/ptrack.db are inert evidence: p-track never reads, migrates, or refuses work because of them, and they can be archived or deleted at any time.

    Safety checklist

    1. Install only the package for the intended OS and CPU.
    2. Keep automatic update checks off unless GitHub checks are wanted.
    3. Treat co-hosted checksums as corruption detection, not an independent signature.
    4. Preserve update journals and rollback artifacts during recovery.
    5. Back up and stop writers before manual database replacement.
