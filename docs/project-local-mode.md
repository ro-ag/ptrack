# Project-local operation and the project overview

## Compatibility contract

The project database remains `.ptrack/ptrack.redb`; the global database remains
`~/.ptrack/global.redb` (or under `PTRACK_HOME`). These features do not change
record encodings, schema versions, table layouts, persistent IDs, or database
identity checks. Project records remain authoritative in the project database.
Local routing metadata and overview summaries are separate files, never database
replicas. Runtime files must remain excluded from version control.

## Access boundary

Enable local operation from a normal terminal with access to the existing global
runtime, while inside the project. Subsequent project commands use the prepared
local binding and identity without opening the global runtime or global database.
Discovery starts at the current directory and is bounded by the project/repository
boundary. Invalid local metadata is an error, not permission to fall back to home.

Commands that require global resources must report that requirement. Explicit
sync runs from the normal terminal: it refreshes the local identity/settings and
the project's global registration and overview summary. It does not empty,
replace, or copy project records into the global database. Repeated sync is safe;
failed sync leaves project records intact. A background synchronizer is outside
this first implementation.

Local sessions do not hold the global maintenance lock while idle. If relocation
or activation changes the database binding, the next local operation fails closed.
Disable local mode from a normal terminal, complete any required relocation, then
enable it again to capture the current binding.

## Overview semantics

The landing page keeps project opening and initialization available alongside an
overview of work tracked in ptrack. Counts describe the latest available cached
project state. The page must identify cache freshness and incomplete coverage;
missing summaries are unknown, not zero work.

The activity view defaults to the last 30 days and also supports all time.
Existing records contain last-update timestamps, not an immutable completion
history. The UI must describe those timestamps honestly and must not infer time
saved or historical completion dates from them. Cached summaries are disposable
and can be regenerated by syncing the corresponding projects or explicitly choosing
Refresh summaries in the desktop landing. Desktop refresh reads only existing,
pinned registry/active-binding matches and updates summary caches. It leaves
project records, registration, and local-mode files unchanged. Unavailable
projects retain prior caches; refresh reports partial results. Automatic landing
loads remain cache-only.

## Acceptance

- Existing databases open without migrations before and after local enable/sync.
- Local reads and mutations succeed when access to global storage is denied.
- Invalid or mismatched local bindings fail closed; global commands cannot
  silently bypass the local access boundary.
- Sync preserves all project records, including mutations made in local mode.
- Opening the overview does not open every project database to calculate stats.
- Partial/missing/stale cache data is visible and does not prevent project access.
- Existing recent-project open, locate, forget, and initialize flows still work.
